# 空气质量时序分析 Agent —— 架构与逻辑实现文档

> 用途：PPT 演示与答辩素材。对应 OHCP 一小时智能编程大赛需求文档 V1.0。
> 项目根目录：`air-quality-agent/`，一键启动：`python web.py`（网页版）/ `python run.py`（命令行版）

---

## 一、项目概述

**一句话定位**：一个自然语言驱动的空气质量大数据分析智能体——用户随口提问，**大模型针对每个问题现生成工具调用链**（function calling 风格），ReAct 引擎按链逐步调度，基于本地真实监测数据完成清洗、聚合、国标超标研判，并以流式方式逐步展示「Agent 自己怎么想、怎么做」，最终输出结构化结论与可视化图表。

- **技术范式**：ReAct（Reasoning + Acting）智能体 + 工具调用链（LLM 规划 / 规则兜底）
- **数据底座**：CN-AIR 公开真实数据集（中国环境监测总站来源，375 城 × 2024 全年逐日，137,250 条记录），**零模拟数据**
- **判定标准**：《环境空气质量标准》GB 3095-2012 二级限值硬编码判定
- **前端展示**：SSE 流式推送 + 消息队列节流，逐步渲染 Thought → Action → Observation
- **课程思政**：随分析业务链路自然融入（国标科普 / 生态感悟 / 业务解读），不弹窗、不说教

## 三、总体架构

```

│              交互层 cli.py ｜ web.py（网页版，SSE 流式）               │
│     命令行对话 ｜ 单条命令 ｜ board 看板 ｜ mode 模板 ｜ 浏览器聊天界面    │
└───────────────────────────────┬─────────────────────────────────────┘
                                │ 自然语言问题
┌───────────────────────────────▼─────────────────────────────────────┐
│                        Agent 层 react_agent.py                       │
│  ┌───────────────────────────────────────────────────────────────┐  │
│  │ planner.py  规划器：LLM function calling（默认）/ 本地规则（兜底）│  │
│  │ 产出「工具调用链」steps = [Step(tool, args, thought), ...]      │  │
│  └───────────────────────────────────────────────────────────────┘  │

│  Thought → Action → Observation 事件（on_event 回调）                │
│  工具注册表: load_data / aggregate / trend / season_exceed /         │
│              anomaly / check_standard / plot_chart / validate       │
│  多轮记忆 memory.py（继承上一轮城市/年份，支撑追问）                     │
└───────────────────────────────┬─────────────────────────────────────┘
                                │ 工具调用
┌───────────────────────────────▼─────────────────────────────────────┐
│            数据层 data_layer.py              分析层 analysis.py       │
│  分片读取(chunksize) + 清洗      聚合统计 / GB 3095 超标判定 /         │
│  （负值、超限、缺失处理）          MAD 异常检测 / 结果校验              │
└───────────────────────────────┬─────────────────────────────────────┘
                                │
┌───────────────────────────────▼─────────────────────────────────────┐
│   数据文件 data/processed/air_quality_2024.csv（137,250 行 tidy 长表）  │
│   原始数据 data/raw（366 个日宽表 CSV，scripts/fetch_data.py 获取）     │
└───────────────────────────────┬─────────────────────────────────────┘
                                │ 分析结果
┌───────────────────────────────▼─────────────────────────────────────┐
│                      输出层 charts.py + report.py                    │
│   PNG 图表（折线/柱状/饼/异常标注，文件名带时间戳）                      │
│   结构化文本 + HTML 报告 + 思政文案                                    │
└─────────────────────────────────────────────────────────────────────┘

网页版流式推送（web.py）：
  浏览器 EventSource ─▶ GET /api/stream ─▶ Agent 后台线程
      每步事件 ─▶ queue.Queue（消息队列缓冲）
      SSE 生成器按单调时钟节流（相邻事件 ≥1s，--interval 可调）依次推送
```

**分层原则**：交互层只负责对话与渲染；Agent 层只负责任务规划与工具调度；数据/分析层只做确定性计算（不依赖大模型）；输出层只做渲染。任何一层可独立替换——例如把 LLM 规划器换成规则规划器，不影响下游任何模块。

## 四、端到端数据流（三个示例问题）

以需求文档中的三个示例提问为例，说明完整链路（规划来源：DeepSeek LLM 实测 / 规则兜底同构）：

```
① 「找出2024年PM2.5年均浓度最高的5个城市，画出月度变化曲线」
   规划器生成调用链: load_data → trend → check_standard → plot_chart(line) → validate
   → load_data      分片读取 137,250 行并清洗
   → trend          未指定城市时取年均 TOP5，算 5 城 × 12 月均值序列
   → check_standard 对照 GB 3095：年均二级限值 35μg/m³，标注各城市是否超标
   → plot_chart     月度变化折线图
   → validate       序列完整性校验
   → report         文本结论（排名表+月度表+超标研判）+ HTML 报告

② 「筛选PM2.5超标记录，统计各省份超标天数占比」
   规划器生成调用链: load_data → aggregate(province, exceed_days)
                     → check_standard → plot_chart(pie) → validate
   → aggregate      按省份统计有效天数/超标天数/占全国比例/省内超标率
                     （城市→省份由 geo.py 内置 375 城映射完成）
   → check_standard 24h 平均二级限值 75μg/m³
   → plot_chart     省份占比饼图
   → validate       占全国比例合计=100% 校验

③ 「统计北京市夏季臭氧O3超标总天数」
   规划器生成调用链: load_data → season_exceed → check_standard
                     → plot_chart(bar) → validate
   → season_exceed  北京 6-8 月 O3 日最大8h平均，对照 160μg/m³ 数超标天数
   → check_standard O3 日最大8小时平均二级限值 160μg/m³
   → plot_chart     超标天数柱状图
   → report         超标研判 + 臭氧危害科普卡片 + 生态感悟
```

**LLM 自适应实例**（规则模式没有这些意图，LLM 现场生成对应调用链）：

| 提问 | LLM 生成的调用链 |
|---|---|
| 广东和江苏哪个省份臭氧污染更严重？ | load_data → check_standard → aggregate(province, exceed_days) → aggregate(province, mean) → plot_chart → validate（双指标交叉验证） |
| 春天的时候全国二氧化氮情况怎么样 | load_data → check_standard → aggregate(season, mean) → plot_chart → aggregate(season, exceed_days) → validate |
| 呼和浩特去年一氧化碳有没有哪天突然飙升 | load_data → anomaly(city=呼和浩特, CO) → plot_chart(line) → validate |

**实测结果**（2024 真实数据）：
- TOP5：和田地区 88.2、喀什地区 56.5、安阳 50.9、鹤壁 50.4、克州 50.0 μg/m³，全部超年均二级限值；
- 省份超标占比 TOP3：河南 14.0%、新疆 10.0%、四川 6.6%（河南 16.2% 的省内超标率为全国最高）；
- 北京夏季 O₃ 超标 45/92 天（超标率 48.9%）；
- LLM 实例：全国 O₃ 超标天数最多省份为山东（占 13.7%）；NO₂ 超标天数冬季占 93.8%；呼和浩特 CO 检出 22 个 MAD 3σ 跳变点。

## 五、核心模块逻辑实现

### 5.1 规划器 `planner.py` —— 自然语言 → 工具调用链

**核心变化**：不再把问题塞进固定「意图枚举」，而是产出**工具调用链** `steps = [Step(tool, args, thought)]`——每个问题都有属于自己的链。

**双模规划**：

| 模式 | 触发条件 | 行为 |
|---|---|---|
| LLM function calling | `.env` 配置 `AQ_LLM_BASE_URL/API_KEY/MODEL` | 把 8 个工具的 JSON schema 交给大模型，它针对每个问题现生成调用链（工具组合、参数自由），任意问法可规划 |
| 本地规则（兜底） | 默认 / LLM 失败 | 槽位识别后生成**同构**调用链，无网无 Key 可跑 |

**LLM 输出契约**：`{"thoughts": [...], "pollutant": ..., "steps": [{"tool", "args", "thought"}]}`。
**清洗与容错**（`_sanitize_llm_steps`）：工具名白名单校验、参数越界钳制（top_n 1-50、年份 2000-2100）、城市名自动校正（北京→北京市、和田→和田地区，`normalize_city`）、缺失 load_data 自动补齐；**任何一步不合法整体回退规则规划器**——比赛现场稳定性优先。
**实测**（DeepSeek）：三个规则模式从未见过的新问法，均生成结构各异的多步链（见第四节表格）。

**槽位识别**（规则模式）：污染物（6 种，兼容大小写与中文别名）、375 城最长匹配、「这几个城市」指代经 memory 继承、年份/季节/TOP N/图表类型自由组合。

### 5.2 数据层 `data_layer.py` —— 分片读取与清洗

- **分片读取**：`pd.read_csv(chunksize=50_000)` 流式迭代，逐块清洗后拼接，不一次性载入原始文件；`discover_years()` 扫描多年份文件，可无缝扩展；
- **清洗规则**：日期/城市缺失行丢弃；负浓度置空；超物理上限（PM2.5>1000 等）置空；AQI 超 500 置空；输出清洗报告（原始行数/丢弃数/缺失率）写入分析口径，**结果可溯源**；
- **省份增强**：内置 375 城→省份映射（`geo.py`），弥补原始数据无省份字段。

### 5.3 数据准备 `scripts/prepare_data.py` —— 原始宽表 → 分析长表

原始数据为小时级宽表（每日一个 CSV：date,hour,type,城市×375），分片转换为「一行=一城一天」tidy 长表：

- `*_24h` 系列：取当日最后非空小时值（滚动 24h 的末日发布值），全空回退小时均值；
- `O3_8h`：取当日 8h 滑动平均的最大值 = **日最大 8 小时平均**（GB 3095 判定口径）；
- `AQI`：取当日最后非空小时值；`质量等级` 由 AQI 按 HJ 633-2012 分级推导（优/良/轻度/中度/重度/严重污染）。

### 5.4 分析层 `analysis.py` —— 统计、国标、异常、校验

- **聚合**：年均浓度排名（带超标标注）、月度趋势透视、省份超标四指标（有效天数/超标天数/占全国比例/省内超标率）、城市超标天数排名、各省平均浓度、**通用分组超标统计**（省份/季节/南北方任意分组，`group_exceed_days`）、城市季节超标、季节与南北方对比；
- **国标判定**：限值表集中于 `config.GB3095_GRADE2`，判定列与限值档一一对应（如 O₃→O3_8h 列对 8h 档 160）；
- **异常检测**：MAD（中位数绝对偏差）3σ 阈值，标记污染突发跳变点；
- **结果校验**（创新点）：占比合计=100%、排名单调递减、样本量充足三重校验，降低大模型规划错误风险。

### 5.5 ReAct 引擎 `react_agent.py` —— 按调用链逐步调度

```
Thought: [规划] LLM 生成本问题专属的 6 步工具调用链      ← 规划器产出
Thought: 先分片读取本地数据集并清洗，确保统计基于真实监测数据
Action: load_data(无参数)
Observation: 已加载 137250 行（375 城市...）
Thought: 按省份统计 O3 平均浓度，覆盖广东与江苏
Action: aggregate(group_by=province, metric=mean, pollutant=O3, year=2024)
Observation: 2024年各省O3平均浓度：共 31 行
...
Action: validate(无参数)
Observation: 通过（样本覆盖 31 个省份，平均浓度降序排列）
```

- **steps 驱动**：引擎不写死流程，严格按规划器的调用链执行；单步失败记录错误事件后继续，不中断整链；
- **事件化**：每步通过 `on_event` 回调发出 Thought / Action / Observation / chart / table / done 事件——网页版据此流式推送，命令行版同一回调自动收集为 trace 文本，**一套内核两种渲染**；
- **工具通用化**：aggregate 支持 group_by（city/province/season/north_south）× metric（mean/exceed_days）自由组合，LLM 可调度任意维度；城市名自动校正；污染物/年份/top_n 全部参数化；
- **图表按结果类型自动选型**（share→饼、trend→折线、anomaly→标注折线、排名→柱状），文件名带毫秒时间戳，保证每次提问看到的都是当次真实计算结果；
- 记忆本轮**实际分析的城市**（非仅提问中提到的），下一轮「再看这几个城市…」自动继承。

### 5.6 输出层 `charts.py` + `report.py`

- **图表**：matplotlib（Agg 无头渲染，不弹窗），中文字体自动探测（微软雅黑/黑体/Noto 等）；折线（月度趋势）、柱状（排名/超标天数）、饼图（省份占比）、异常标注折线；
- **文本结论**：固定结构【分析任务】【统计口径】【统计结果】【超标研判】【图表输出】【结果校验】；
- **HTML 报告**：浅色主题，图表相对路径引用，含思政区块与 Agent 执行轨迹，生成后自动打开浏览器；
- **思政融入点**（随业务输出，共 3 处）：①超标研判附带国标限值科普；②污染物危害科普卡片；③结尾「环境小感悟」（绿水青山就是金山银山，1-2 行，不堆砌）。

| CO | 24h 平均 | 4 mg/m³ | CO_24h |

## 八、关键设计决策与权衡

1. **为什么用 Python 而不是 Java/langchain4j**：一小时约束下 pandas+matplotlib 生态最成熟、出图零浏览器依赖、环境配置风险最低；语言选型不影响 ReAct 范式与工具链设计的展示。
2. **为什么自研轻量 ReAct 而不是直接上 LangChain**：①比赛现场可能无网无 Key，规则规划器保证 100% 可演示；②减少框架版本依赖事故；③ReAct 循环与工具注册表本身完整可讲，不依赖框架黑盒。
3. **为什么选 CN-AIR 而不是天池原集**：天池镜像需登录且数据截至 2023-05，而需求示例要 2024；CN-AIR 源自中国环境监测总站（需求中的备选数据源），含完整 2024，且自带 PM2.5_24h / O3_8h，与 GB 3095 判定口径天然对齐。
4. **大模型只做规划、不做计算**：读取/清洗/统计/超标/绘图全部由本地工具完成，符合需求「禁止直接让大模型编造分析结果」的硬约束；LLM 仅解析意图，失败可回退。
5. **思政融入的位置选择**：绑定在超标研判与结果末尾两个业务节点，保证「随分析结果一并输出」，不做独立弹窗。

## 九、演示脚本建议（60 分钟）

**时间分配**：10min 审题+工具设计 → 40min 编码调试 → 10min 提交展示。

**上台步骤**：
1. `python web.py` 一键启动网页版，浏览器打开，顶部显示「规划：LLM（deepseek-flash）」；
2. 输入示例①，**观看调用链卡片 + 步骤逐条流出**（每步间隔 1s，Thought→Action→Observation 清晰可读）+ 排名表 + 折线图；
3. 输入示例②，展示省份饼图与校验通过；
4. 输入示例③，展示北京夏季 O₃ 45 天超标 + 科普卡片；
5. **换一个规则模式没有的问法**（如「广东和江苏哪个省份臭氧污染更严重？」），展示 LLM 现场生成的双指标交叉验证链——证明 Agent 不是查表；

## 十、风险与兜底

| 现场风险 | 兜底方案 |
|---|---|
| 无网络 / 无 API Key | 规则规划器默认工作，全链路本地完成；网页版 `/api/status` 实时显示规划来源 |
| LLM 超时 / 返回非 JSON / 工具名非法 / 参数越界 | `_sanitize_llm_steps` 白名单校验 + 整体回退规则规划器，演示不中断 |
| LLM 请求了不支持的工具组合（如 season+exceed_days 早期版本） | 单步记录错误事件继续执行；组合能力已补齐（province/season/north_south × mean/exceed_days） |
| matplotlib 中文字体缺失 | 启动时自动探测 7 种常见中文字体，失败退英文标注 |
| 提问方式与示例不同 | LLM 针对每个问题现生成调用链；规则模式槽位覆盖自由组合，无法识别时默认全国 PM2.5 年均排名 |
| 数据年份不符 | Agent 按提问年份过滤；数据仅含 2024，问其他年份会明确提示数据范围 |
| 图表不弹窗 | HTML 报告始终落盘 `outputs/reports/`，网页版图表内联展示，可手动双击打开 |
| LLM 输出占全国比例 100.1% | 校验阈值 ±1% 容差，通过并如实展示合计值 |
